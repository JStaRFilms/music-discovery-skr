Failure found and fixed in this run: Transformers 5.21 returns
`BaseModelOutputWithPooling` from CLAP feature calls instead of a bare
tensor. The first smoke attempt crashed with `AttributeError` on
`.detach`. `features_to_numpy` in `src/music_discovery/embed.py` now
unwraps `pooler_output`, with regression tests in `tests/test_embed.py`.

## Run 2 — broken checkpoint found by the judge, fixed same day

John judged 21 rows of run 1 and reported the same songs repeating. He was
right, and the pack was withdrawn. Investigation, in order:

- The 75 run-1 results came from only 5 distinct tracks, reshuffled for
  every query. The same passage answered contradictory prompts.
- A tight repro (`music-discovery check-model`) showed why. For
  `laion/larger_clap_music` at `a0b4534a…`, unrelated probe texts scored
  0.998–0.999 cosine against each other. The checkpoint's text tower
  collapses on this stack, so every prompt effectively asked the same
  question and the same hub windows won.
- Differential evidence cleared the pipeline. With identical code and
  Transformers 5.21: `laion/clap-htsat-fused` scored 0.10–0.24 across
  unrelated texts, `laion/clap-htsat-unfused` 0.06–0.31, and
  `laion/larger_clap_music_and_speech` -0.02–0.32. The defect is in the
  music-only checkpoint, not in the extraction path.
- Fix: primary model switched to `laion/larger_clap_music_and_speech`
  at `195c3a3e…` (music-trained, Apache-2.0). The health check now fails
  the rejected checkpoint at 0.9994 and passes the new primary at 0.6238.
  A regression integration test stands behind it.
- John's 21 marks are preserved at
  `experiments/judgements-run1-broken-checkpoint.xlsx`. Several of his
  notes identify the repetition directly. The marks stay as evidence of
  the failure. They are not scored as retrieval quality.
